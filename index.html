Ellie

Computer Science undergraduate at Government Engineering College, Thrissur, reading for a B.Tech in Computer Science and Engineering.

I build small tools that run entirely in the browser — parsers, editors and design utilities with no framework, no build step and no dependencies. The interesting part of each one is usually the thing underneath: an RFC 4180 reader that survives a comma inside an address, a cubic-bezier solver that falls back to bisection when Newton's method diverges, a path-data scanner that knows arc flags can be packed together.

I care about the parts people skip. Correct edge cases, honest error messages, keyboard access, and interfaces that say what they did rather than reporting a single number.

How I work

A few things that show up in everything above.

  • Write the engine first. Every tool starts with the parser or the solver, tested on its awkward cases, before a single pixel is placed.
  • No dependencies unless they earn it. Eight projects, zero npm packages at runtime. It keeps the code readable and the pages fast.
  • Say what happened. A tool that reports "42% smaller" is less useful than one that lists what it removed.
  • Accessibility is not a pass at the end. Focus rings, contrast ratios and reduced motion are commits in the history, not a checklist.
